# M4-02 发现：映射表登记的是「观测面」，求解器需要的是更大的「存在面」

- 日期：2026-09-10
- 发现方式：适配器路径第一次真正驱动求解（`--adapter=on`），逐个崩溃暴露
- 影响层级：**架构级**——它触及 M3-03 的「commit 派生规则 ↔ 映射表 model_ready 行 双向双射」这条不变量

## 1. 现象

适配器路径在 `Fem.f90:10752`（`predict`，由 `static_u` 调用）以

```
forrtl: severe (408): Attempt to fetch from allocatable variable ORDER_TIME_MDOFN
                      when it is not allocated
```

中止。此时它已经走完 startup、整个块循环、`model_ready`、PROFILE SET 与
`phase_ready`，进入了第一个增量——**也就是说前面每一步都在适配器状态上跑通了**。

`order_time_mdofn` 是 `.glb` 的一条记录（`Global.f90:957`），M1 注册表登记了这个 reader
（`GLB.global_data.order_time_mdofn`），**适配器也确实解析了它**
（`src/adapter/yl_adapter_model.f90:220`）。但：

- **M2 映射表里没有它的任何一行**（`grep` 只命中一条提到它的 note）；
- 因此 commit 不写它；
- 因此适配器路径上它从未被分配，而 `predict` 每个自由度都要读它一次。

M1 给它的分类是 `state_target = "unused_switch"`、`consumers = "dynamic time integration"`。
**这个分类对「值有没有作用」是对的，对「有没有被读」是错的**——静力路径每个增量都读。
与 `stab_matde` 同一形态：**靠阅读做出的分类，被执行推翻。**

## 2. 这不是一处疏漏，是两个面的系统性差异

机械清点（`global_data` 在适配器接入点之后分配的数组 vs `commit_legacy_globals` 写入的集合）：

> **`global_data` 分配 54 个不同的数组，commit 写其中 9 个。**

其余 45 个里有少数是 `stat=`/`errmsg=` 之类的误命中，也有相当一部分在静力路径上因守卫为假
而根本不分配。但方向是清楚的，而且 `order_time_mdofn` 已经证明**「值不被观测」不蕴含
「不需要存在」**。

根因可以一句话说清：

> **映射表回答的是「我们比较什么」，求解器要的是「什么必须存在」。**
> 这两个集合此前一直可以当成同一个，只是因为**在适配器真正驱动求解之前，
> 从来没有第二个东西需要「存在」这一面。**

M3-03 判据 19 那条双射（commit 的 46 条 derive 规则 ↔ 映射表 model_ready 行，
Fortran 侧断言正向与单射、Python 侧断言反向）正是把这两个角色钉成了一个。
它当时是对的，而且抓到过真实缺陷；现在它成了约束。

## 3. 为什么不能用现成的两条路绕开

**(a) 把这些行补进映射表并让 commit 写它们** —— 需要这些行**被发出**（`emit`），因为残余集合
（`deck_residue_t` 的 27 个分量）是**从快照携带的行里计算**出来的
（`tools/yl_state_map.py:2159`：`residue = {fid for fid in want ...}`，`want` 是发出行）。
而一旦发出面变大，**冻结基线就少了字段**，值级比较会判结构差异 → 必须重新冻结。
`yl_state_probe.py freeze` **故意是一次性且无 `--force`** 的，理由写在它自己的模块头里，
ADR-0006 又重申过：**基线的价值来自它不跟着实现走。**

**(b) 让适配器自己分配这些数组** —— 直接违反 M4-01 的硬约束
「不得新增第二个 legacy 全局 writer」。那条约束不是洁癖：快照在检查点读全局，
它不知道第二个 writer 还没跑完。

**(c) 把接入点挪到 `global_data` 的分配段之后** —— 做不到。分配与读取是交错的
（数组尺寸来自刚读到的值），没有一条把两者分开的线。

## 4. 建议的解法：把两个角色拆开，各自配一个双射

**保留映射表作为「比较面」，另建一张「存在面」表**：

- 新表逐行登记**求解器要求存在、但其值不进比较面**的 legacy 数组，
  每行必须写明**为什么它的值不需要被观测**（例如「静力路径上恒为 0 且其消费者是 no-op」），
  以及**它的值从哪来**（deck 记录 / 派生 / 常数零）；
- `commit_legacy_globals` 增加一段只按这张表写入的代码，出处账本增设
  `EXISTENCE_ONLY` 桶；
- **原双射不被削弱，而是变成两条**：比较面 ↔ derive 规则，存在面 ↔ 存在段写入；
  两条都用集合相等，不用充分条件（沿用 L2-c 折叠那次「出口条件曾经可以被一个谎言满足」的教训）；
- **冻结基线不动**，因为存在面不进快照。

代价：commit 变成两段，读者必须同时理解两张表。
收益：**「必须存在」这件事第一次有了一个可清点、可对账的落点**，
而不是散落在 `global_data` 里靠一次次崩溃发现。

## 5. 已经走通的部分（不受本冲突影响）

- 接入点落在 `global_data` 的**文件打开之后、第一条读取之前**（`Global.f90:690`，
  一条原本就空的行），所以 legacy 的全部单元照常打开，而 79 条 `.glb` 读取一条都不执行；
- `commit_legacy_globals` 在 `--adapter=on` 下成功，所有权闸门通过；
- 适配器状态支撑求解走完 startup、块循环、`model_ready`、PROFILE SET、`phase_ready`，
  进入第一个增量；
- legacy 侧改动仍然**不改变任何文件的行数**：`Fem.f90` 18 行就地前缀 + 1 行清空，
  `Global.f90` 1 行（原空行）。三个检查点锚点与全部 reader 注册表站点行号未动。
