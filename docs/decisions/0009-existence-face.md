# ADR-0009：拆开「观测面」与「运行存在面」，各配一条独立双射

- 状态：接受（负责人 Huijun，2026-09-10）；**准入规则于 2026-09-11 由负责人改写，见 §准入纪律**
- 相关：`docs/m4/M4-02-finding-observation-vs-existence.md`（冲突的完整记录）、
  ADR-0006（冻结基线是值级、不可重新冻结）、M3-03 判据 19（commit 规则 ↔ 映射表双射）、
  M4-01 硬约束（不得新增第二个 legacy 全局 writer）

## 背景

适配器路径第一次真正驱动求解时，在 `Fem.f90:10752`（`predict`）以
`ORDER_TIME_MDOFN ... not allocated` 中止。

`order_time_mdofn` 是 `.glb` 的一条记录：M1 登记了 reader，适配器解析了它，
**而 M2 映射表里没有它的任何一行**，所以 commit 不写它。M1 的分类是
`unused_switch` / 「动力时程用」——**对「值有没有作用」是对的，对「有没有被读」是错的**：
静力路径每个自由度、每个增量都读一次。与 `stab_matde` 同一形态：
**靠阅读做出的分类，被执行推翻。**

机械清点表明这不是孤例：`global_data` 在适配器接入点之后分配 **54** 个数组，
commit 写其中 **9** 个。

根因：

> **映射表回答「我们比较什么」，求解器要的是「什么必须存在」。**
> 这两个集合此前能当成同一个，只因为在适配器真正驱动求解之前，
> 从来没有第二个东西需要「存在」这一面。

两条现成的路都堵死：把这些行补进映射表需要它们**被发出**（残余集合从发出行计算），
发出面一变冻结基线就过期，而 `freeze` 故意一次性无 `--force`（ADR-0006）；
让适配器自己分配则直接违反 M4-01 的「不得新增第二个 legacy 全局 writer」。

## 决策

**保留映射表作为比较面，另建存在面表，两者各配一条独立的双射。**

- **表**：`docs/m4/existence-face.toml`。每行登记一个 legacy 数组：符号、载体分量名、
  模块、范围、dtype、值的来源（deck / 派生 / 常零）、deck reader id、
  legacy 原分配位点、**`observed_requirement`**（demanded 它的那次真实中止，含站点）、
  以及 `why_not_on_compare_face`。
- **载体**：`src/problem/yl_problem_existence.f90` 的 `deck_existence_t`，
  与 `deck_residue_t` 平行但**必须是另一个类型**——residue 的成员是从映射表**发出行**
  计算出来的，存在面的行按定义不在发出行里。
- **写入**：`commit_legacy_globals` 增加一段**存在面 pass**，在**同一个 WRITE 阶段**里，
  因此**不产生第二个 legacy 全局 writer**。
- **门禁**：`tools/yl_existence_check.py`，全部是**双向集合相等**（不用充分条件——
  L2-c 折叠的出口条件曾经可以被一个谎言满足，就是因为用了充分条件）：
  - **E0** 每行必须有 `observed_requirement`；
  - **E1** 表的行 == `deck_existence_t` 的标记，且分量名 == 表的 `carrier`；
  - **E2** 表的行 == commit 存在面 pass 写入的符号 == `commit_release` 释放的符号
    （写而不释放是泄漏；释放而不写是对本模块不拥有的存储下断言）；
  - **E3** 表的符号与映射表**发出**的 legacy 符号**不相交**——
    一个被比较的值不得同时被登记为「不被观测」；真要两边都要，**映射表赢**。
  五个阴性对照各恰好触发一条，其余沉默。

**M3-03 的单条双射不被削弱，而是变成两条。** 把两者合并才是削弱：
**一张表同时表示两件事，正是「被比较」与「必须存在」当初被混为一谈的机制。**

## 准入纪律（2026-09-11 由负责人改写）

**初版规则是「一行只有在真实运行为了它中止之后才被加入」。负责人于 2026-09-11 改写为：**

> **机械清点接入点之后所有必须存在的状态，建立完整 runtime manifest，
> 并用真实求解推进验证，不要逐项手工猜。**

**改写的理由，实践已经给出**：按崩溃逐项加行，只能学到**已经崩过的那些**；
它对「存在但恰好没崩」的状态一无所知，而那正是最危险的一类——
`element%nrfields` 不崩，它只是让装配循环跑零次，把 gravity 算对的单元荷载丢掉，
而三个检查点的 190 个发出字段全部一致。**一个只会在崩溃后学习的规则，
看不见这种缺陷。**

**现在的机制**：

- `tools/yl_runtime_scan.py` 从接入点扫到 `global_data` 结尾，逐条报出分配、维度、
  所在守卫、随后的初始化与源码行；它**不作判断**；
- `docs/m4/runtime-state-manifest.toml` 为**每一个候选**记一个处置
  （`required` / `unreachable`），并写明理由；
- `tools/yl_runtime_manifest_check.py` 的 **E4** 断言清单覆盖扫描的每一个候选，
  **E5** 断言判为 `unreachable` 的行**没有**被写入——
  建立 legacy 没有的状态是反方向的偏离，一样看不见；
- **验证由真实求解给出**：两个 golden 算例在 `--adapter=on` 下跑完并与参考**逐值相同**。

`observed_requirement` 仍然保留在那些**先由崩溃发现**的行上，作为它们的来历记录；
机械清点出来的行用 `why` 记录扫描依据。E0 要求二者至少有其一。

## 标量（2026-09-11 补）

扫描最初只看 `allocate`，因此看不见标量。`alfa_p4` 是暴露这一类的那一个：
`-init=snan` 下适配器路径在 `modf_element_lib` 的 `if (alfa_p4 > 0)` 上陷入，
而 legacy 路径干净跑完。

**73 个 `.glb` 标量由 `tools/yl_runtime_gen.py` 生成三件东西**——载体类型、
parse_glb 侧的填充块、commit 侧的写入块与 `use` 列表。**生成而不是手写**：
七十三个分量、七十三条赋值、七十三条写入，是七十三次打错的机会，而打错是无声的。

其中只有 parse_glb **确实读到**的那些被载体携带；其余由 `global_data` 的内部例程读取，
`parse_glb` 里根本没有同名局部量，生成器据此排除并在清单中记录原因。

## 值仍然来自 deck

「它的值不被比较」**不等于**「可以写个常数」。两个 golden deck 上
`order_time_mdofn` 全是 0，第三个 deck 未必。`stab_matde` 是现成的教训：
两个 deck 都是 99999，把这个常数钉死会静默毁掉另一个 deck。

## 代价与收益

- 代价：commit 变成两段；读者要同时理解两张表。
- 收益：**「必须存在」第一次有了可清点、可对账的落点**，
  而不是散落在 `global_data` 里靠一次次崩溃发现；冻结基线不动；
  比较面的语义一个字没改。
