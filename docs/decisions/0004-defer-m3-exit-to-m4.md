# ADR-0004：M3 延后出口，bridge 状态等价随 M4-01 一并签收

- 状态：接受
- 日期：2026-09-08

## 背景

M3 的三个任务（M3-01 类型、M3-02 流水线、M3-03 build_runtime/commit）已全部交付。
但 `02-migration-plan.md` 给 M3 定的第四条出口条件是：

> bridge 后的 state fingerprint 与原路径一致

`07-acceptance-and-release.md` 的验收表把它写成 M3 必需证据里的「bridge 状态等价」。

**这条在 M3 内做不到。** 它需要把真实 golden 算例（256 单元的 Cook 膜、64 单元的 Lamé 筒）
表示成 `problem_state_t`，而"旧 deck → ProblemState"的通路是 **M4 的第一项任务**
（"将旧 reader 拆成只构建 ProblemState 的适配器"）。仓库里目前没有任何这样的通路：
M3-02 的正向 fixture 是缩到 1 个 Q4、4 节点的**结构等价体**，不是基准网格。

这是在 M3-03 实施到测试层才发现的：套件要与 `cases/golden/*/reference/frozen.json` 逐值比对，
才发现无从构造被比对的一侧。

`07` 末尾已有一句「M0 验收不依赖 M2 状态工具；各门按上表开始适用，避免循环依赖」——
说明立项时已意识到循环依赖的风险，但这一处漏掉了：**M3 的出口条件依赖 M4 的产出。**

## 决策

1. **M3 阶段延后出口**。M3-01/02/03 三个任务各自保持 DONE；阶段签收推迟到 M4-01 完成后一并进行。
2. **「bridge 状态等价」的举证责任移到 M4-01**。M4-01 交付适配器后，用它把两个基准算例
   构建成 `ProblemState`，走 `build_runtime` → `commit_legacy_globals`，再与冻结基线逐值比对。
   届时同时结清 M3 和 M4 的这条证据。
3. **不修改 M3 的出口条件文字**，只在验收表标注它与 M4 合并签收。改文字会让"当初要求过什么"消失，
   而这份计划的价值之一正是它记录了当初的要求。

## 后果

- M3 的实现质量与它是否出口解耦：三个任务的证据（自检 108/108、桥接 581/581、反向双射、
  build-id 不变）照常有效，但**没有任何一行的值与 M2 冻结基线比对过**，这一点写在
  `docs/m3/M3-03-runtime.md` §8，不因阶段延后而淡化。
- M4-01 的验收矩阵变重：它同时承担自己的「独立进程新旧差分」和 M3 遗留的「bridge 状态等价」。
- **风险登记**：若 M4-01 发现 `build_runtime` 的某个派生与 legacy 不等价，缺陷已经积压了整个 M3 阶段。
  这是延后出口的直接代价，接受它是因为替代方案（在 M3 内先造一个一次性 reader）会在 M4-01 之前
  制造第二套 deck 解析语义，两套语义此后必然漂移。

## 备选方案及不选的理由

- **在 M3 内写一个最小 deck 读取器**：能立刻比对基线，但那是在 M4-01 之前先造一个平行适配器。
  两套 deck 解析语义并存，此后每次方言修正都要改两处——正是 ADR-0001 拒绝"生成旧文本"时
  所依据的同一类理由。
- **把冻结基线的比对降级为"结构比对"**：只比形状与非零模式、不比值。这会让出口条件名存实亡，
  且与 M2-03 已冻结的逐值基线不相称。
