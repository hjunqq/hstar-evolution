# 质量门与停止规则

测试 ID、容差和反例按 [测试规格](06-test-specification.md) 实施，适用阶段及判决以
[验收流程](07-acceptance-and-release.md) 为准。工具未实现或环境缺失必须标 NOT_RUN/BLOCKED。
下列要求针对受影响的已开放能力；M0 不以尚未开发的 M2 状态工具作为前置条件。

## 每次提交

- Fortran 编译无新增 warning；
- 输入和状态单元测试通过；
- 不改变未涉及能力的 state fingerprint；
- 新错误路径有负向测试；
- 不新增从 modern 路径读取 legacy deck 的行为。

## 每个迁移子阶段

| 质量门 | 判据 |
|---|---|
| Build | 支持平台的 Debug/Release 及编译器可用的运行时检查通过；不可用检测及第三方盲区单列 |
| Input | schema、单位、引用、范围和组合检查通过 |
| State | 新旧入口状态相同，或差异被逐字段批准 |
| Numerical | 位移、反力、应力、特征值等在各自容差内 |
| Physics | 解析解、patch test、守恒或消融关系通过 |
| Failure | 所有登记坏输入可控退出且消息可定位 |
| Capability | 白名单和证据等级更新 |
| Documentation | 用户输入、限制和迁移说明完整 |

## 必须停止扩展的情况

出现以下情况时，当前能力不得继续增加字段或算例，必须先修基础层：

- 相同输入产生非决定性 state fingerprint；
- 输入错误仍能导致崩溃或半初始化；
- 新旧结果不同但无法定位到入口状态或明确算法修改；
- 为了跑通而添加无法解释的默认值；
- 一个字段在两个路径拥有不同语义；
- 自动回退掩盖 modern 解析或验证失败；
- 只有历史结果、没有物理判据，却准备标记 production。

## 差异处置

所有差异只能归入三类：

- `REGRESSION`：应保持但发生变化，必须修复；
- `INTENTIONAL_FIX`：确认旧行为错误，保留旧基线并新增修复后的物理证据；
- `EXPECTED_REFORMULATION`：算法或离散方式明确变化，需要独立基准和版本说明。

禁止以“新结果看起来合理”关闭差异。

## 一个反复出现的缺陷形状：声明与被声明之物未绑定

M4-01 期间同一形状出现了九次。它值得单列，因为**没有一次是靠阅读发现的**——每一次都是踩上去，
或是被一个专门去攻它的反例逼出来的。

| # | 声明 | 实际 |
|---|---|---|
| 1 | W4 守卫的名单声称覆盖它 move_alloc 的全部记录数组 | 漏了 `trans`，正是该守卫存在要防的那扇门（M3-03 Round-2） |
| 2 | `bridge_test` 断言 `group%np_unode` | 那是 `group_of_elements` 自己的分量；要守的 `unode_elements%np_unode` **同名不同物**，隔两层 |
| 3 | 提交 `cded7f4` 的信息写「重新生成 dump 使溯源行与 map 一致」 | 没做到：dump 写 `8ec26e625672`，map 是 `5224c8aa06f7` |

| 8 | `verify_problem_inputs` 头部：「**every** ProblemState scalar the staging pass reads must actually be SET」 | 实际覆盖 8/13；未覆盖的五处就在被修的那几行下面 |

### 一个测试侧的亚种：断言的名字声称了夹具做不到的区分

上表九例都在「被测物」一侧。第十例在**测试**一侧，更隐蔽：

`bridge_test` 有一条断言字面叫做「`group(:)%matno` 是 `sections[].material`，不是 `.material_header`」，
用来抓取值来源被调换。**它抓不到**——夹具把这两个字段都设成了 1，调换 commit 的来源不改变任何结果，
rc=0、零失败。**断言的名字读起来就是证据，而它声称的区分在夹具里不可能发生。**

最值得记的是：设计 §5.2 早已写下这个风险（「两者在 golden deck 上恰好相等，所以错误不可见」），
**写在文档里并没有阻止作者写出这条抓不到的断言**。这是「写进文档」与「做成门禁」之间差距的直接证据。

修复的位置也是要点：**修夹具，不修断言**。一个职责是抓「来源被调换」的夹具，
**必须在真实 deck 恰好相等的地方制造差异**——否则它验证的是巧合，不是行为。

推论：**凡断言的名字里出现「是 A，不是 B」，就必须检查夹具里 A ≠ B**，否则那条断言只是一句注释。

### 第二个测试侧亚种：拒绝之后的路径没有定义的失败模式

比上一个更隐蔽，因为**两个复核者会拿到两个不同的结果，而两个都不是证据**。

`bridge_test` 的 `build_and_commit` 在 commit 被拒绝后**仍然无条件调用 `check_landed`**，
而被拒绝的提交按定义没有 `move_alloc` 任何 legacy 全局。于是 `:513` 的
`element(ie)%ldofs` 解引用一个未分配的 allocatable——**UB**，是否 fault 取决于进程内存布局。

实测：两位复核者用**逐字相同**的编辑（在同一处插入 `if (i == 1) cycle` 强制丢弃一条记录），

- 一方：段错误（rc=174），崩在 `:513`，从未执行到 `:584` 的 `prescrib` 断言；
- 另一方：干净返回 rc=6，执行了 `:584`，读的是未分配的 `prescrib` 全局。

两次都报出「17 个连带失败」且「0 个 `prescrib` 值断言失败」——**而这两个数字都不是证据**：
17 只是**恰好没有 fault 的那些读取**，0 在一边是「没跑到」、在另一边是「读了未定义内存」。

**危害不在崩溃，在于它看起来像结论。** lead 曾据此报告「我设的硬要求已满足」，
而那个观测来自一条无定义行为的路径。要求成立，验证不成立。

**推论：凡「机制拒绝之后」的观测，在拒绝后的路径被定义之前，一律不算证据。**
这直接影响每一个「断言前提并拒绝」式的设计——它们的验证方式都是同一形状。
修法：拒绝之后只报**一条** finding（拒绝本身及其原因），跳过值遍历。
其对照必须在**两棵不同的构建树**上各跑一次——差异既然源于地址空间，一次通过不足以说明问题消失。

### 第十二例：一次测量证明了缺陷存在，被当成了缺陷边界

这一例是 lead 的，形状与前十一例相同但成因不同——**不是清单照着上一个 bug 写，而是从一次测量过度推广**。

lead 实测「删掉 `props%mechanical%solid` 的释放，release 与 MSan 都全绿」，据此在设计 §5.1.3 写下：

> `props` 是唯一的两级链，因此是**唯一处于该盲区中的对象**。

前半句成立，**后半句不由它推出，而且是错的**。两次后续测量推翻它：

- dev-fold2 删掉 `tcurves(i)%ttime_curve`（**一层**指针）的释放 → 979/979 全绿；
- lead 删掉 `prescrib(i)%leldofix`（**M3-03 时期就存在**的一层指针）的释放 → release 979/979、MSan 979/979。

盲区与链的层数无关，它关于**任何经由一个已被释放的全局才能到达的对象**，
范围是 `commit_release` 的**全部 20 处内层指针释放**，且**先于整个折叠工作存在**。

**教训**：一次反例证明的是「这里有一个洞」，**不是**「洞只有这么大」。
把「我测到的那个」写成「唯一的那个」，会让后续所有人按一个错误的边界安排验证——
本例里它差点让 valgrind 出口条件只用一个阳性对照，从而只证明 valgrind 能工作、
不证明其余 19 处干净。

**推论**：任何形如「X 是唯一处于该情形的对象」的断言，**必须由枚举支撑，不能由一次测量支撑**。
枚举是廉价的（本例是对 `commit_release` 的一次 grep），过度推广的代价不是。

### 两个根因

**其一：清单照着「上一个缺陷的形状」写，而不是照着它声称覆盖的面写。** 第 8 例的作者自述：
「第一版是照着引发它的那次失败（一个未设定的 `opt_int`）写的，不是照着 staging pass 写的。」
第 3、第 6 例同源。**写守卫时，作用域必须从被保护面推导，不能从触发它的那个 bug 推导。**

这条还有一个可识别的**危险时刻**：这三处都写在**引发它们的那个缺陷刚被发现之后**——
那正是**被保护面最不可见、而具体失败最鲜明**的时刻。所以「刚修完一个 bug、顺手加一道守卫」
是本项目里最需要停下来重新枚举被保护面的时点，而不是最可以信任的时点。

**其二：机器核对的那一半修了，人读的那一半还在说旧数字。** 第 6、7、8 例都是这个形态。
第 7 例给出了最直接的证据：两位复核者各自认真读同一段注释，**一个漏掉了最要害的那一句，
另一个漏掉了其余五句，两人各漏一半**。这不是谁不细心——**靠人读去查陈旧数字不可靠**。

### 有效的对策：让两侧可以各自被改，而不一致时必须响

凡是能被机械对账的，就不要用注释约定。本阶段建立并经反例验证过的对账有：

- 规则表 ↔ 映射表的**反向双射**（`yl_state_map.py runtime-rules`）
- 出处账本 ↔ 映射表的**集合等式**（`commit-provenance`）——等式没有充分条件那种「哪条碰巧成立就放行」的入口
- staging 读取 ↔ 输入检查的**包含关系**（`commit-inputs`），**提取前先剥离注释**，使散文无法冒充覆盖
- 生成物 ↔ 来源的 **sha256 溯源**（`build.sh`，fail-closed）
- 映射表散文 ↔ 冻结基线的**取值对拍**（`yl_map_selfcheck.py`，自带阳性对照）
- 分量名 ↔ `@map` 标记的**双向相等**

共同性质：**两侧是两个可以各自被编辑的东西，任一侧单独变动都会响。** 单侧自报的声明一律不算证据。

### 与反例纪律的关系

见 `07-acceptance-and-release.md`「反例（阴性对照）的有效性」。这里补一条：**上表九例里，
有五例是在为修复前一例而新写的机制上发现的**——第 9 例长在为修复第 8 例而新增的检查里。
所以每加一道门禁，都要把「这道门禁自己声称覆盖什么、实际覆盖什么」当作下一个要攻的目标。
